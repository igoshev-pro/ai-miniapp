🎯 Назначение

TelegramContext — единая точка доступа к Telegram WebApp SDK для всех компонентов приложения. Решает три задачи:

Инициализация SDK при загрузке (один раз)
Детекция режима: Telegram Mini App vs обычный браузер
Прокидывание API в любой компонент через useTelegram()
🏛️ Архитектура

Структура файла


1. Imports (lib/telegram + React)
2. interface TelegramContextValue       — публичный API контекста
3. const TelegramContext = createContext — с no-op дефолтами
4. function applySafeArea(wa)            — хелпер для CSS-переменных safe area
5. function TelegramProvider             — провайдер (logic + useEffect-ы)
6. function useTelegram                  — хук-обёртка для useContext
Провайдер использует 3 useEffect-блока:

1️⃣ Init effect (mount-once, [])

Получает webApp через getWebApp() из @/lib/telegram
Детектит реальный Telegram: !!wa.initData && wa.initData.length > 0
Это ключевое решение: SDK создаёт window.Telegram.WebApp даже в обычном браузере, но initData будет пустой → это и есть критерий
Если в Telegram:
wa.ready() — сообщает Telegram'у что WebApp загружен
wa.expand() — разворачивает на полный экран
wa.setHeaderColor('#0a0a0a') + setBackgroundColor('#0a0a0a') — синхронизация с дизайн-системой
wa.setBottomBarColor('#0a0a0a') — только если версия >= 7.10
wa.enableClosingConfirmation() — подтверждение при выходе
applySafeArea(wa) — установка --safe-area-top сразу
Подписка на safeAreaChanged + contentSafeAreaChanged events
Двойной retry: setTimeout(applySafeArea, 500ms) + setTimeout(..., 1500ms) — workaround для гонок при загрузке
setWebApp(wa), setIsTelegram(true)
Если в браузере:
setWebApp(null), setIsTelegram(false)
В конце: setIsReady(true) — флаг для SpichkiApp (показывать ли loading screen)
2️⃣ Viewport effect ([webApp])

Только если webApp инициализирован
Слушает viewportChanged event Telegram'а
Обновляет CSS-переменные на каждое изменение viewport:
--tg-viewport-height: ${webApp.viewportHeight}px
--tg-viewport-stable-height: ${webApp.viewportStableHeight}px
Перезапускает applySafeArea при изменении viewport
Cleanup: offEvent
3️⃣ Theme effect ([webApp])

Слушает themeChanged event
Устанавливает атрибут data-color-scheme на <html> (light/dark)
Cleanup: offEvent
⚠️ Важно: пока в globals.css есть только dark-тема, поэтому data-color-scheme фактически не используется. Заготовка под будущее.

🔧 applySafeArea(wa) — Safe Area Logic

Telegram WebApp предоставляет два набора insets:

safeAreaInset.top — системный safe area (notch, status bar)
contentSafeAreaInset.top — safe area внутри Telegram (header чата)
Итоговая логика:

Ts

const total = safeTop + contentTop
const isPhone = platform.includes('ios') || platform.includes('android')
const minOffset = isPhone ? 44 : 0  // минимум 44px на iOS/Android
const offset = Math.max(total, minOffset)

document.documentElement.style.setProperty('--safe-area-top', offset + 'px')
🎯 Зачем minOffset = 44: гарантирует что на iPhone (где notch ~44px) хедер всегда отступает, даже если Telegram не вернул корректные insets.

CSS использует эту переменную в globals.css:

Css

.sticky-header { padding: var(--safe-area-top, 0px) 16px 0 16px; }
.chat-page__model-bar { top: calc(var(--header-height) + var(--safe-area-top, 0px)); }
📦 Публичный API (TelegramContextValue)

Состояние

Ts

🔌 Зависимости от @/lib/telegram (не получены)

Из импортов видно, что src/lib/telegram.ts содержит:

🚦 Жизненный цикл


1. Mount TelegramProvider
2. useEffect [] → getWebApp()
   ├─ window.Telegram?.WebApp exists?
   │   ├─ Yes → initData непустой? 
   │   │   ├─ Yes → init Telegram (ready, expand, colors, safe area)
   │   │   │       setWebApp(wa), setIsTelegram(true)
   │   │   └─ No  → setWebApp(null), setIsTelegram(false) [браузер]
   │   └─ No  → setWebApp(null), setIsTelegram(false) [нет SDK]
   └─ setIsReady(true)
   
3. webApp changed → подписки на viewportChanged, themeChanged
4. Children renders with context value
5. Unmount → cleanup всех event listeners

⚠️ Замеченные проблемы

🔴 Критичные

Дублирование кода в сообщении — артефакт чата, файл физически один.

body.tg-app класс НЕ выставляется в этом провайдере, хотя CSS (globals.css) активно его использует для override всех desktop-стилей. Где-то это происходит — нужно искать. Логично было бы:

Ts

if (isRealTelegram) {
  document.body.classList.add('tg-app')
}
Hardcoded colors в showMainButton:

Ts

color: '#FACC15',          // вместо var(--accent-yellow)
text_color: '#0A0A0A',     // вместо var(--bg-primary)
Telegram WebApp API принимает только hex-строки, но цвета должны браться из дизайн-токенов через JS (например getComputedStyle).

Hardcoded #0a0a0a в setHeaderColor / setBackgroundColor / setBottomBarColor — то же самое.

🟡 Средне

as any для событий:

Ts

wa.onEvent('safeAreaChanged' as any, ...)
wa.onEvent('contentSafeAreaChanged' as any, ...)
Тип WebApp в lib/telegram.ts не включает эти события — нужно дополнить тип.

Двойной retry safe area (setTimeout(500) + setTimeout(1500)) — workaround для гонок. Хрупкое решение, но рабочее. Лучше слушать event'ы.

showBackButton НЕ удаляет старые callbacks:

Ts

webApp.BackButton.onClick(callback)  // добавляет
webApp.BackButton.show()
При повторном вызове накопятся обработчики. Использующие компоненты (например ChatPage) делают это вручную через offClick, но публичный API контекста хрупкий.

👉 Поэтому в реальности компоненты минуют этот метод и работают с webApp.BackButton напрямую:

Tsx

useEffect(() => {
  webApp?.BackButton.show()
  webApp?.BackButton.onClick(handler)
  return () => {
    webApp?.BackButton.offClick(handler)
    webApp?.BackButton.hide()
  }
}, [...])
hapticFn, hapticNotificationFn, hapticSelectionFn не зависят от webApp (они импортируются напрямую). Это значит, что в браузере (где нет WebApp) они должны no-op'ить — это валидируется внутри @/lib/telegram, но из контекста это не видно.

enableClosingConfirmation() всегда включён — может раздражать пользователей. Хорошо бы вызывать только когда есть unsaved state (например незавершённый стриминг чата).

Нет обработки errors: если wa.ready(), wa.expand() или setHeaderColor бросят — приложение крашнется. Нужны try/catch.

MainButton: цвета хардкодом:

Ts

color: '#FACC15'  // не из CSS-переменных
🟢 Минор

Контекст с no-op дефолтами — это анти-паттерн. Лучше бросать ошибку если useTelegram использован вне провайдера:

Ts

export function useTelegram() {
  const ctx = useContext(TelegramContext)
  if (!ctx._initialized) throw new Error('useTelegram outside provider')
  return ctx
}
platform: string — мог бы быть union type 'ios' | 'android' | 'web' | 'tdesktop' | 'macos' | 'unknown'.

startParam не пробрасывается дальше — компоненты могут использовать его для deep linking (например реферальный код, открытие конкретного чата), но в коде нигде нет его обработки. Возможно неиспользуемая фича.

Нет viewport_changed events для desktop — на тач-устройствах viewport меняется когда открывается клавиатура. На desktop этого не происходит, но эффект всё равно подписывается.

🎯 Архитектурные решения

Single source of truth для TG SDK: все компоненты получают доступ только через useTelegram(), не через window.Telegram.WebApp напрямую.

⚠️ Но в MediaResult.tsx (Блок 4) обнаружено нарушение этого правила:

Ts

const tg = (window as any).Telegram?.WebApp
if (tg?.downloadFile) { ... }
Должно быть через хук.

Lazy initialization: всё происходит в useEffect, не блокирует первый рендер. До получения SDK показывается loading screen (см. SpichkiApp).

Graceful degradation:

В браузере webApp = null, но контекст не падает
Все методы безопасные — webApp?.method()
haptic в браузере не делает ничего
Reactivity через events: viewport и theme изменения обрабатываются реактивно, CSS-переменные обновляются.

isReady gate: вместе с authReady и hydrated контролирует когда приложение готово отрендериться (SpichkiApp ждёт всех троих).
